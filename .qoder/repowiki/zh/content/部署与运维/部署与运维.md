## 简介
本文档旨在为运维人员提供一套完整、稳定、可靠的生产环境部署方案。涵盖从Docker镜像构建、容器运行、Kubernetes多环境部署管理到生产环境配置优化的全流程指导，确保系统在不同环境中的一致性与高可用性。

## Docker镜像构建与容器运行

本项目通过 `Dockerfile` 实现后端服务的容器化打包，并提供 `docker.sh` 脚本用于构建和运行容器。

### Dockerfile 构建流程
`Dockerfile` 定义了镜像的构建步骤，基于 `loads/alpine:3.8` 轻量级基础镜像，将编译后的二进制文件、配置文件、资源文件等打包进容器。

- **工作目录**：`/app`
- **文件拷贝**：
  - `hack/` 目录：包含启动配置
  - `manifest/config/`：核心配置文件
  - `resource/`：静态资源
  - 编译后的 `hotgo` 二进制文件
  - `entrypoint.sh` 启动脚本
- **权限设置**：为二进制文件和启动脚本添加可执行权限
- **启动命令**：通过 `CMD ./entrypoint.sh` 执行启动脚本

### docker.sh 脚本作用
`docker.sh` 是一个占位脚本，当前为空，可用于在 `docker build` 前执行预处理命令（如环境检查、文件生成等）。实际构建由 `Makefile` 中的 `image` 目标调用 `gf docker` 命令完成。

## Kustomize多环境部署管理

项目使用 Kustomize 实现不同环境（开发、测试、生产）的部署差异管理，通过 `base` 基础配置和 `overlays` 覆盖配置实现环境差异化。

### 基础配置 (base)
位于 `manifest/deploy/kustomize/base/`，包含所有环境共用的 Kubernetes 资源定义：
- `deployment.yaml`：定义应用部署的基本结构
- `service.yaml`：定义服务暴露方式
- `kustomization.yaml`：声明资源列表

**Section sources**
- [kustomization.yaml](file://server/manifest/deploy/kustomize/base/kustomization.yaml#L1-L9)
- [deployment.yaml](file://server/manifest/deploy/kustomize/base/deployment.yaml#L1-L22)
- [service.yaml](file://server/manifest/deploy/kustomize/base/service.yaml#L1-L13)

### 环境覆盖 (overlays)
以 `develop` 环境为例，位于 `manifest/deploy/kustomize/overlays/develop/`：
- **继承基础配置**：通过 `resources: - ../../base` 引入 base 配置
- **环境专属配置**：
  - `configmap.yaml`：定义开发环境的 `ConfigMap`，包含日志级别为 `all`，便于调试
  - `deployment.yaml`：通过 `patchesStrategicMerge` 覆盖基础 Deployment，指定镜像为 `template-single:develop`
- **命名空间**：部署到 `default` 命名空间

此结构允许为不同环境（如 `test`、`prod`）创建独立的 overlay 目录，实现配置隔离。

## Kubernetes部署清单解读

### Deployment 解读
- **元数据**：名称为 `template-single`，标签为 `app: template-single`
- **副本数**：`replicas: 1`，生产环境建议根据负载调整为更高值
- **选择器**：匹配标签为 `app: template-single` 的 Pod
- **容器配置**：
  - 容器名：`main`
  - 镜像：`template-single`（基础）或 `template-single:develop`（开发）
  - 镜像拉取策略：`Always`，确保每次部署都拉取最新镜像

### Service 解读
- **类型**：ClusterIP（默认）
- **端口映射**：
  - 服务端口：`80`
  - 目标端口：`8000`（容器内服务监听端口）
- **选择器**：将流量路由到标签为 `app: template-single` 的 Pod

### ConfigMap 解读
`configmap.yaml` 将配置文件 `config.yaml` 挂载为 ConfigMap，内容包含：
- **Server 配置**：监听地址 `:8000`，OpenAPI 和 Swagger 路径
- **Logger 配置**：日志级别 `all`，输出到标准输出，适用于开发环境调试

## Makefile便捷命令说明

`Makefile` 提供了一系列便捷命令，简化开发和部署流程。

### 核心命令
- **`make build`**：一键编译。先编译前端项目并复制静态资源到后端目录，然后编译后端 Go 代码。
- **`make image`**：构建 Docker 镜像。使用 `gf docker` 命令，通过 `-tn` 参数指定镜像名和标签（如 `hotgo:v1.0`）。
- **`make deploy`**：部署到 Kubernetes。根据 `TAG` 环境变量（默认 `develop`）选择对应的 overlay 目录，使用 `kustomize build` 生成最终 YAML 并通过 `kubectl apply` 部署。同时对 Deployment 执行 patch 操作，更新标签以触发滚动更新。
- **`make start`**：一键启动。依次执行 `image`、`deploy` 和 `port`（端口转发），快速部署并访问服务。

### 其他实用命令
- `make all/http/queue/cron`：通过 `gf run` 热编译启动对应服务
- `make web`：启动前端开发服务器
- `make refresh/clear`：刷新或清理 Casbin 权限
- `make dao/service`：生成 DAO 和 Service 层代码
- `make cli`：安装或更新 GoFrame CLI 工具

## 生产环境配置建议

为确保生产环境的稳定性、性能和安全性，建议进行以下配置优化：

### 数据库连接池
- **最大连接数**：根据数据库服务器性能和应用并发量设置，建议初始值为 50-100。
- **空闲连接数**：保持一定数量的空闲连接以减少创建开销，建议为最大连接数的 1/4。
- **连接超时**：设置合理的连接获取超时时间（如 5s），避免请求堆积。

### 日志级别
- **生产环境**：将日志级别调整为 `info` 或 `error`，避免 `all` 或 `debug` 级别产生过多日志，影响性能和存储。
- **日志输出**：关闭 `stdout` 输出，将日志写入文件或集中式日志系统（如 ELK）。

### 安全设置
- **镜像来源**：使用可信的基础镜像（如官方 Alpine），并定期更新以修复安全漏洞。
- **最小权限原则**：容器以非 root 用户运行。
- **环境隔离**：不同环境使用独立的 Kubernetes 命名空间和配置。
- **敏感信息**：数据库密码等敏感信息应通过 Kubernetes Secret 管理，而非硬编码在 ConfigMap 中。
- **网络策略**：配置 NetworkPolicy 限制 Pod 间的网络访问。

### 高可用性
- **副本数**：Deployment 的 `replicas` 应设置为大于 1（如 3），并配合健康检查（liveness/readiness probe）实现高可用。
- **资源限制**：为容器设置 `resources.limits` 和 `requests`，防止资源耗尽。

## 总结
本文档详细介绍了基于 Docker、Kustomize 和 Makefile 的生产环境部署方案。通过 `Makefile` 可以高效地完成构建、镜像打包和 Kubernetes 部署。Kustomize 的 base/overlays 模式实现了多环境配置的有效管理。运维人员应根据生产环境的实际需求，调整数据库连接池、日志级别和安全配置，确保系统的稳定、高效和安全运行。
